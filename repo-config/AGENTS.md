# AGENTS.md — 写作与质量公约（全局 / 项目通用）

> 本文件由 agent（dsh / pi / zcode）自动加载，写任何文字都必须遵守。
> 可放用户级全局位置（dsh 为 `~/.dsh/AGENTS.md`），也可放单个仓库根；内容相同。
> 仓库内 openwiki 会在本文件维护一段 `<!-- OPENWIKI:START --> … <!-- OPENWIKI:END -->` 指针块，本公约写在那个块之外，openwiki 更新时不会覆盖。

## 全局铁律（回复 / 文档 / 注释 / PR 描述一律适用）

1. **读者模型**：假设读者有基础代码知识 + 前序需求知识，但没有本次内容的任何先验知识。
2. **结论先行**：先给结论/总览，再展开；去套话，每句话都有信息，不写废话。
3. **术语唯一**：一词一义；术语必须来自「当前项目的 openwiki 术语表」；查不到就标 `[待定]`，严禁自造词。
4. **结构可见**：先总览后细节、零跳跃、从简到繁，像受欢迎技术博客一样通俗言简。

## 统一写作方法论：双阶段写作法（拆解 → 展开）

> 适用范围：模型回复、软件设计文档、性能分析、SQL 分析、项目汇报、wiki 等一切文字产出。
> 本段是唯一权威，内联在此以保证始终生效；仓库 `methodology/writing-methodology.md` 是分享/引用副本，改动后需同步本文件。

### 0. 核心思想（一句话）

**写作 = 先为自己做结构化思考（拆解），再为读者做渐进式表达（展开）。**
两个阶段目标不同、读者不同，必须分开做。

| | 阶段一 · 拆解 | 阶段二 · 展开 |
|---|---|---|
| 读者 | 你自己（设计者） | 零先验知识的开发者 |
| 目标 | 完整、精确、清晰 | 零负担、零跳跃读懂 |
| 本质 | 无损压缩（把需求压成最小完整骨架） | 无损展开（把骨架展开成可读文档） |
| 产出 | 脑图 / 骨架 | 正式文档 |

### 1. 阶段一 · 拆解（脑图 / 骨架）

#### 原则
- **A1 穷举**：所有关键点无遗漏地归类。
- **A2 迭代重构**：反复拆分 / 调整 / 重新分类，直到类间**互斥且穷尽**（MECE），边界清晰。
- **A3 原子命名**：每个节点只写「高度精简准确的几个字」，不写句子。
- **A4 重点下钻**：复杂逻辑 / 算法 / 全新知识，对节点单独展开说明。
- **A5 多图分维**：大而复杂的需求 → 多张脑图跨维度拆；某块重要且不拆会乱 → 独立成图。

#### 验收标准（阶段一完成的定义）

> **设计者本人看到这份脑图，加上自己对项目的先验知识，能够把整个新需求精确、完整、清晰地表述出来。**

关键：脑图不是给外行看的完整文档，而是「设计者凭先验知识能 100% 复原需求的最小压缩包」。此时文档**已经完整**，只是尚未**展开**。

### 2. 阶段二 · 展开（正式文档）

#### 读者模型（写作第一约束，动笔前必须显式声明）

- **有**：基础代码知识 + 前序需求知识
- **无**：本次新需求的任何先验知识（因为只有设计者参与了思考）

#### 通用原则（对所有文档生效，不因场景而变）

- **B1 渐进披露**：先给总览，再逐层展开；先整体后局部、先易后难、从简单到复杂。
- **B2 零跳跃**：每一步都是上一步的自然延伸，读者**不需要脑补**任何中间步骤。
- **B3 通俗言简**：参照受欢迎的技术博客——通俗易懂、言简意赅、读着舒服。
- **B4 术语唯一**：一词一义；术语必须来自权威词表（代码真实命名 / 术语表）；查不到就标 `[待定]`，严禁自造词。

#### 总览层形态（因场景而异，由场景技能指定）

「先总览后细节」的**原则不变**，但总览层长什么样由场景决定：

| 场景 | 总览层形态 | 展开顺序 |
|---|---|---|
| 软件设计文档 | 架构图/流程图 + 改动点列表 | 图 → 改动点 → 逐点细节 |
| 性能分析文档 | 结论 + 数据摘要 | 结论 → 数据 → 分析 → 结论 |
| SQL 分析文档 | 分析目标 + SQL 总览 | 目标 → SQL → 逐段解释 → 性能说明 |
| 项目汇报 | 结论 + 进展/风险/下一步 | 结论 → 三块分述 |
| wiki 分享 | 概念图 + 目录 | 概念 → 由浅入深 |

#### 验收标准（阶段二完成的定义，通用四问）

用「零先验知识开发者」的视角自问：

1. 只看总览层（图/结论/列表），能不能 30 秒 get 到整体？
2. 看完总览，知不知道下面要讲哪些点、重点是什么？
3. 逐层读下去，每一步跟得上、没有跳跃吗？
4. 有没有哪一句需要读者「自己脑补」才能往下读？——有，就补上。

> 第 4 问是灵魂。「零跳跃」的反面不是写错，而是少写一步、让读者脑补。

### 3. 两阶段之间的桥

```
脑图的分类   →  文档的章节
脑图的关键点 →  文档总览层的列表（如改动点）
```

阶段一是「把复杂变简单」，阶段二是「把简单讲清楚」。

### 4. 强度两档

| | 正式文档（设计/分析/汇报/wiki） | 日常回复 |
|---|---|---|
| 走脑图 | 走完整「拆解」 | 不走，直接答 |
| 用 | 完整双阶段 | 轻量版：读者模型 + 结论先行 + 言简 + 术语准 |

### 5. 四症状对照（自查用）

| 症状 | 解药 |
|---|---|
| 自造词 | A3 原子命名 + B4 术语唯一 |
| 啰嗦 | A3 精炼 + B3 言简 + B1 各层只说该层的话 |
| 条理乱 | A2 迭代重构 + B2 零跳跃 |
| 结构乱 | A1/A5 完整结构 + B1 总览可见 |

## 写正式文档时（强制）

写任何文档（设计文档 / 分析 / 汇报 / wiki / spec 等），不论使用哪个 skill：

1. 先按上文「阶段一 · 拆解」的 A1–A5 和验收标准输出脑图骨架；
2. 输出脑图后停下，等我确认；**不确认，不展开**；
3. 确认后再按「阶段二 · 展开」展开正文；
4. 展开完过「通用四问」自检。

> 日常聊天回复走轻量版（见「强度两档」），不强制脑图。

## 与第三方 skill 的对接（映射）

使用开源 skill（grill-me、superpowers/brainstorming、openspec/explore、openspec/proposal 等）时，把它们接到方法论的对应阶段；不改动第三方 skill 本身：

| 第三方 skill | 方法论阶段 | 用法 |
|---|---|---|
| superpowers / brainstorming | 拆解·输入（A1 穷举、A5 多维度） | 先发散，再把产出做 MECE 归类成脑图 |
| openspec / explore | ≈ 拆解（理解问题、摸清边界） | 直接当拆解阶段用 |
| 任何产出文档的 skill（如 openspec/proposal） | ≈ 展开（写文档） | 展开前必须先输出脑图骨架确认，该 skill 的结构当展开模板 |
| grill-me | 拆解后的骨架验证 | 用它对脑图做压力测试，等价于「骨架先确认」 |

三原则：
1. 不改第三方 skill 本身（其升级会覆盖本地改动）。
2. 映射只写在本公约，不写进第三方 skill。
3. 任何 skill 的产出最终都要过「通用四问」，不满足就回炉。

典型链：brainstorming 发散 → 脑图拆解（MECE / 原子命名 / 重点下钻）→ grill-me 验证骨架 → 展开 → 通用四问自检。

## 评审一篇既有文档时（不新造技能）

用方法论的「通用四问」逐条检查，列出所有需要脑补/跳跃的点，并给出修改建议。

## 术语源（治自造词）

- 术语必须来自「当前项目的 openwiki 术语表」，术语表六列：中文术语 / English / 代码真实命名 / 定义 / 别名禁用词 / 出处。
- 代码里不存在、且团队尚未约定的术语，禁止凭空创造；必须提及时标 `[待定]`。
